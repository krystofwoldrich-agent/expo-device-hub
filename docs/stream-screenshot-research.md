# Android Emulator `streamScreenshot` research

Research date: 2026-09-02. The moving upstream branches are pinned here to the revisions inspected: Android Emulator proto [`4e74507c`](https://android.googlesource.com/platform/tools/base/+/4e74507c931f725836deee44cd0cea04155d1d19/emulator/proto/emulator_controller.proto), emulator server [`ae9d18d2`](https://android.googlesource.com/platform/external/qemu/+/ae9d18d2b6261179fbd57fffec720a04f7bfb053/android/android-grpc/services/emulator-controller/server/src/android/emulation/control/EmulatorService.cpp), Android Studio [`dfe5a699`](https://android.googlesource.com/platform/tools/adt/idea/+/dfe5a699e0316e799fc615a0faf2ed97fd24eabc/streaming/src/com/android/tools/idea/streaming/emulator/), and `serve-emu` [`c4f1c051`](https://github.com/expo/serve-emu/tree/c4f1c05192d0d9300b12addac604581fc7ca2ca6).

## Bottom line

`getScreenshot` is unary: one request produces one complete `Image`. `streamScreenshot` is server-streaming: one request remains open and produces a complete `Image` whenever the emulator has new content or a relevant sensor update. Neither RPC returns an H.264 stream. The available payload formats are PNG, four-byte RGBA8888, and three-byte RGB888; H.264 exists only if a client adds a downstream encoder ([RPC definitions](https://android.googlesource.com/platform/tools/base/+/4e74507c931f725836deee44cd0cea04155d1d19/emulator/proto/emulator_controller.proto#284), [format and image messages](https://android.googlesource.com/platform/tools/base/+/4e74507c931f725836deee44cd0cea04155d1d19/emulator/proto/emulator_controller.proto#1391)).

The selected experimental `serve-emu` revision already implements that split. Its video data plane is a long-lived RGB888 `streamScreenshot`; its unary PNG `getScreenshot` calls remain only for initial native geometry/display wake-up and as a fallback when the native display-size signal changes ([session startup and stream request](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/grpc-session.ts#L1394-L1507), [geometry monitor](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/grpc-session.ts#L747-L795)). Therefore, implementation work should preserve the stream and decide separately whether those control-plane unary probes can be removed; replacing the probes is not required to stop frame polling.

## Exact protocol contract

### Request and sizing semantics

Both RPCs accept one `ImageFormat`. `format` is field 1, desired width and height are fields 3 and 4, display is field 5, and optional side-channel transport is field 6. Display `0` or omission means the main display ([`ImageFormat`](https://android.googlesource.com/platform/tools/base/+/4e74507c931f725836deee44cd0cea04155d1d19/emulator/proto/emulator_controller.proto#1391)).

Width and height are a bounding box, not a request to distort the image: the emulator preserves aspect ratio and returns dimensions no larger than the requested bounds or the real display. Passing `0` for either dimension selects native display dimensions in the emulator implementation; orientation may swap the output dimensions ([proto contract](https://android.googlesource.com/platform/tools/base/+/4e74507c931f725836deee44cd0cea04155d1d19/emulator/proto/emulator_controller.proto#284), [server sizing implementation](https://android.googlesource.com/platform/external/qemu/+/ae9d18d2b6261179fbd57fffec720a04f7bfb053/android/android-grpc/services/emulator-controller/server/src/android/emulation/control/EmulatorService.cpp#922)). A stream request is immutable, so changing the render target requires cancelling it and opening another stream. Android Studio does exactly that when its view bounds or orientation change ([Studio feed sizing and restart](https://android.googlesource.com/platform/tools/adt/idea/+/dfe5a699e0316e799fc615a0faf2ed97fd24eabc/streaming/src/com/android/tools/idea/streaming/emulator/EmulatorView.kt#701)).

### Payload and metadata

The wire values and byte counts are:

| `ImgFormat` | Value | Payload |
| --- | ---: | --- |
| `PNG` | 0 | One complete PNG byte sequence; variable length |
| `RGBA8888` | 1 | One complete image, four bytes per pixel |
| `RGB888` | 2 | One complete image, three bytes per pixel |

These values and byte widths are part of the proto ([format enum](https://android.googlesource.com/platform/tools/base/+/4e74507c931f725836deee44cd0cea04155d1d19/emulator/proto/emulator_controller.proto#1391)). The `Image.image` field contains the complete payload. Its documented pixel organization is left-to-right and bottom-up. It is empty when MMAP transport is selected because the bytes then live in the caller-owned side channel ([`Image`](https://android.googlesource.com/platform/tools/base/+/4e74507c931f725836deee44cd0cea04155d1d19/emulator/proto/emulator_controller.proto#1445), [`ImageTransport`](https://android.googlesource.com/platform/tools/base/+/4e74507c931f725836deee44cd0cea04155d1d19/emulator/proto/emulator_controller.proto#1355)). The current `serve-emu` request type exposes only format, width, and height, so it uses the default main display and inline gRPC bytes rather than MMAP ([request encoding](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/emulator-grpc.ts#L372-L388)).

Returned width, height, format, and rotation live under `Image.format`; top-level `Image.width` and `Image.height` are deprecated. `Image.seq` is a `uint32`: the first streamed screenshot is documented as sequence 0, a unary screenshot is always sequence 0, and stream values need not be contiguous. A positive gap is explicitly intended to count frames that did not arrive. `timestampUs` is the emulator's estimated Unix timestamp in microseconds before the frame is copied and transformed ([image fields](https://android.googlesource.com/platform/tools/base/+/4e74507c931f725836deee44cd0cea04155d1d19/emulator/proto/emulator_controller.proto#1445)).

The server source explains why gaps are expected: it waits for framebuffer events, obtains the number accumulated, advances `seq` by that count, and writes one reply. Thus `seq` measures source-side coalescing/loss as well as any later client-side loss, rather than promising a contiguous message counter ([stream loop](https://android.googlesource.com/platform/external/qemu/+/ae9d18d2b6261179fbd57fffec720a04f7bfb053/android/android-grpc/services/emulator-controller/server/src/android/emulation/control/EmulatorService.cpp#762)).

### Stream lifecycle and errors

The stream sends when a new frame or sensor change is available; it is not a timer-driven polling RPC. Its first response can be empty (`width = 0`, `height = 0`) when the display is inactive. It emits another empty image when a visible display becomes inactive and resumes images when it becomes active ([stream contract](https://android.googlesource.com/platform/tools/base/+/4e74507c931f725836deee44cd0cea04155d1d19/emulator/proto/emulator_controller.proto#306)). `streamScreenshot` reports `INVALID_ARGUMENT` for an invalid/disabled display and `CANCELLED` when the context is cancelled. Unary `getScreenshot` additionally documents `FAILED_PRECONDITION` for a non-PNG fast-path request before the guest has posted a frame ([RPC contracts](https://android.googlesource.com/platform/tools/base/+/4e74507c931f725836deee44cd0cea04155d1d19/emulator/proto/emulator_controller.proto#284)).

PNG encoding is explicitly called CPU-intensive, while MMAP can reduce pixel-transport overhead ([stream performance notes](https://android.googlesource.com/platform/tools/base/+/4e74507c931f725836deee44cd0cea04155d1d19/emulator/proto/emulator_controller.proto#318)). RGB888 is consequently the appropriate inline format for the existing RGB-to-H.264 pipeline; PNG is suitable for an occasional standalone screenshot or geometry probe, not a smooth high-rate stream.

## Android Studio's reference behavior

Android Studio provides a useful first-party consumer implementation:

- It derives the requested dimensions from the physical pixels currently available to the view, leaves room for a rendered device frame, clamps to actual display/environment dimensions, requests RGB888, and restarts only when that demand changes ([view-size calculation](https://android.googlesource.com/platform/tools/adt/idea/+/dfe5a699e0316e799fc615a0faf2ed97fd24eabc/streaming/src/com/android/tools/idea/streaming/emulator/EmulatorView.kt#701)).
- It sizes the gRPC inbound limit to `maxDisplayPixels * 3 + 100`, explicitly allowing three bytes per RGB888 pixel plus protobuf overhead ([channel sizing](https://android.googlesource.com/platform/tools/adt/idea/+/dfe5a699e0316e799fc615a0faf2ed97fd24eabc/streaming/src/com/android/tools/idea/streaming/emulator/EmulatorController.kt#226)). RGBA8888 would require four bytes per pixel instead.
- It disables both the generic gRPC compressor and decompressor registries. This is separate from choosing PNG versus RGB; PNG is an image format, whereas gRPC compression wraps the protobuf message ([channel construction](https://android.googlesource.com/platform/tools/adt/idea/+/dfe5a699e0316e799fc615a0faf2ed97fd24eabc/streaming/src/com/android/tools/idea/streaming/emulator/EmulatorController.kt#277)).
- It uses a custom image marshaller with a reusable byte array and aliasing, and warns that the returned image bytes cannot outlive `onNext`. It then synchronously unpacks RGB into a reusable same-sized `BufferedImage` raster ([stream lifetime warning](https://android.googlesource.com/platform/tools/adt/idea/+/dfe5a699e0316e799fc615a0faf2ed97fd24eabc/streaming/src/com/android/tools/idea/streaming/emulator/EmulatorController.kt#653), [marshaller buffer reuse](https://android.googlesource.com/platform/tools/adt/idea/+/dfe5a699e0316e799fc615a0faf2ed97fd24eabc/streaming/src/com/android/tools/idea/streaming/emulator/EmulatorController.kt#1237), [image reuse](https://android.googlesource.com/platform/tools/adt/idea/+/dfe5a699e0316e799fc615a0faf2ed97fd24eabc/streaming/src/com/android/tools/idea/streaming/emulator/EmulatorView.kt#1330)).
- Its processing and display handoffs are `AtomicReference` single slots. A newer frame replaces the pending one instead of joining a stale FIFO, and `seq` gaps plus replacement counters feed dropped-frame diagnostics ([newest-only handoffs](https://android.googlesource.com/platform/tools/adt/idea/+/dfe5a699e0316e799fc615a0faf2ed97fd24eabc/streaming/src/com/android/tools/idea/streaming/emulator/EmulatorView.kt#1409), [`seq` accounting](https://android.googlesource.com/platform/tools/adt/idea/+/dfe5a699e0316e799fc615a0faf2ed97fd24eabc/streaming/src/com/android/tools/idea/streaming/emulator/EmulatorView.kt#1346)).

Buffer reuse has an ownership constraint: a buffer cannot be recycled while an asynchronous encoder, upload, or texture update still reads it. Studio can alias the gRPC buffer because it consumes it synchronously inside `onNext`. `serve-emu` currently retains `latest.image` for later ffmpeg writes and idle repeats, so adopting the same marshaller literally would corrupt frames; it needs either a synchronously consumed destination buffer or a small ownership-aware pool.

## Audit of the experimental `serve-emu` implementation

The implementation originated in [`9aca37e`](https://github.com/expo/serve-emu/commit/9aca37e75526663a81cffe5859224c9cdebdc057). The following `34d1945` did not change the two capture files; [`c4f1c051`](https://github.com/expo/serve-emu/commit/c4f1c05192d0d9300b12addac604581fc7ca2ca6) added capture timing/drop diagnostics without changing the core RPC choice.

### What is already aligned

- The hand-written HTTP/2 client encodes the canonical format numbers, reads output dimensions from nested `Image.format`, and decodes `seq` plus `timestampUs` ([protobuf codec](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/emulator-grpc.ts#L372-L448)).
- Session capture requests one RGB888 server stream bounded by `maxSize × maxSize`; the emulator preserves aspect ratio. The default `maxSize` is 1280 and `0` means native ([stream request](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/grpc-session.ts#L1493-L1507), [shared defaults](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/scrcpy.ts#L118-L131)).
- `GrpcMessagePacer` pauses the HTTP/2 readable side after an emission, retains at most the newest already-parsed pending protobuf from the current chunk, and emits at most once per `maxFps` slot. `grpc-session` similarly keeps one `latest` source image for the next encoder write rather than a raw-frame FIFO ([message pacer](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/emulator-grpc.ts#L621-L757), [latest-frame scheduling](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/grpc-session.ts#L952-L1059)).
- It sends uncompressed gRPC request envelopes, advertises no compression encoding, and rejects any response envelope whose compressed flag is set. This is an identity-only implementation, although the policy is implicit in framing rather than represented as a named channel option ([framing and rejection](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/emulator-grpc.ts#L508-L566), [request headers](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/emulator-grpc.ts#L789-L817)).
- The latest revision separately counts raw messages received/emitted/coalesced, positive `seq` gaps, source timestamp intervals, production-to-receive latency, and encoder backpressure ([diagnostics tracker](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/grpc-session.ts#L54-L177)).
- Each accepted RGB frame is re-encoded by host ffmpeg/libx264 into the existing H.264 `VideoPacket` contract. That downstream encoding does not change the fact that the emulator RPC itself transports complete raw images ([encoder input](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/h264-encoder.ts#L348-L486)).

### Gaps and risks to address before production

1. **Resolution demand is server-wide, not display-driven.** The source receives a square `maxSize` bound chosen from CLI/runtime encoder settings. It does not know the physical pixel size of either UI, and it does not reopen the source solely because a UI viewport changed. This meets a coarse longest-edge cap, but not “request only as many pixels as the UI can display.” A shared device stream needs an explicit aggregation rule, such as the maximum current physical-pixel demand among active viewers, capped by administrator/CLI policy, with debounced restart when that aggregate materially changes.

2. **The receive limit is fixed rather than derived.** The parser caps every inbound message at 64 MiB and validates the length before allocation ([limit and parser](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/emulator-grpc.ts#L17-L18), [length check](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/emulator-grpc.ts#L518-L569)). That safely covers common 1280 and 4096 RGB bounds, but `grpc-session` accepts `maxSize` through 16,384, whose worst-case RGB payload is far above 64 MiB ([validation](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/grpc-session.ts#L898-L913)). Compute a checked per-stream limit greater than `requestedWidth × requestedHeight × bytesPerPixel + protobuf overhead`, then reject requests above a documented absolute memory ceiling. For native (`0`) sizing, probe or otherwise learn the native maximum before opening the stream.

3. **Per-frame allocation remains.** `GrpcMessageParser` calls `Buffer.allocUnsafe(length)` for every message. Newest-only retention bounds the live queue, but it does not eliminate high-rate allocation and garbage collection ([parser allocation](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/emulator-grpc.ts#L540-L594)). Introduce ownership-aware reusable storage at the gRPC-to-encoder seam; never overwrite the buffer currently owned by Node's writable queue. If a future UI receives raw images directly, use the same latest-only rule and reuse its canvas/WebGL/WebGPU texture allocation when dimensions are unchanged.

4. **Empty images are silently filtered.** `isUsableRgbFrame` rejects width/height zero, and `onImage` simply returns, so display-inactive transitions are not surfaced; the idle path can continue encoding the last visible image ([validation](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/grpc-session.ts#L505-L513), [receiver](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/grpc-session.ts#L1165-L1184)). Treat the protocol's empty image as a display-state event, not malformed data. During startup, it is reasonable to wait for a non-empty frame with a deadline; after readiness, consumers should receive an inactive state rather than a stale live picture.

5. **Drop metrics need layered interpretation.** `sequenceGaps` is calculated only across decoded/emitted usable images. It combines frames skipped inside the emulator, frames withheld by HTTP/2 backpressure, and frames replaced by the client pacer. `rawGrpcMessagesCoalesced` identifies only the subset already present in a parsed chunk ([pacer events](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/emulator-grpc.ts#L691-L716), [sequence accounting](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/grpc-session.ts#L123-L151)). Keep the layers separately named and handle stream restart/`uint32` wrap so a new sequence epoch cannot be mistaken for normal loss.

6. **Contract-level orientation needs an emulator fixture.** The official contract says the result is oriented from coarse device orientation and documents raw rows as bottom-up. The adapter passes RGB bytes onward and adds a separate ffmpeg rotation based on ADB state. Verify portrait and all three rotated states against a labeled test pattern before preserving that transform; normalize row order and orientation once, inside the adapter, so capture consumers never guess ([proto orientation](https://android.googlesource.com/platform/tools/base/+/4e74507c931f725836deee44cd0cea04155d1d19/emulator/proto/emulator_controller.proto#284), [local geometry transform](https://github.com/expo/serve-emu/blob/c4f1c05192d0d9300b12addac604581fc7ca2ca6/packages/serve-emu/src/grpc-session.ts#L523-L575)).

## Recommended implementation sequence

1. Preserve `getScreenshot` only as a bounded bootstrap/native-geometry fallback; use exactly one `streamScreenshot` call per active capture generation for frame delivery.
2. Normalize a render demand into physical-pixel width and height plus an administrator cap. Open RGB888 at those bounds, and debounce cancel/reopen when aggregate UI demand changes.
3. Derive and enforce the inbound limit before opening the stream; explicitly keep generic gRPC compression disabled.
4. Make the raw-frame handoff a one-current/one-pending ownership model. Coalesce before expensive decode/copy where possible, and recycle buffers only after the encoder/renderer releases them.
5. Model empty images, cancellation, clean completion, non-OK gRPC status, decode failure, and first-frame timeout explicitly. A clean, unexpected end is still a session failure.
6. Preserve `seq` and `timestampUs` through diagnostics. Report emulator sequence gaps, client replacements, encoder rejections, and viewer/network drops as separate counters.
7. Verify with a fake adapter and a real-emulator matrix: fragmented envelopes; oversize and compressed envelopes; RGB length; empty-active-empty transitions; `seq` gaps/restart/wrap; cancellation; viewport resize; portrait/landscape/reverse orientations; bounded memory under an over-producing emulator; and no stale-frame FIFO under an intentionally slow encoder.
